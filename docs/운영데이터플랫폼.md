# 숙박 운영 데이터 플랫폼 기능 요구사항

## 1. 시스템 개요
### 1.1. 목적

OTA 예약·정산 파일과 직접 예약을 하나의 데이터로 모아 다음을 가능하게 한다.

- 플랫폼/채널별 매출·수수료·순매출 파악
- 현장 관리비, 외부 소유주 정산을 자동 산출하고 근거를 남김
- 고정비·변동비 입력을 통한 객실 유형별 손익 파악
- 수요 예측과 가격 추천 (장기)

### 1.2. 운영 구조

| 업소 | 객실 | 비고 |
|---|---|---|
| 선셋코스트 카라반&캠핑장 | 카라반 14 (스페이스카라반 4, 에어스트림 5, 카라반 5) | 성수기 10월, 8월은 비수기 |

- 가족 사업자 간 정산은 참고용 리포트 수준으로만 제공한다.

## 2. 데이터 수집
### IMPORT-01 파일 업로드

프론트는 파일만 업로드한다. 플랫폼과 파일 종류는 서버가 판별한다.

| 플랫폼 | 예약 파일 | 정산 파일 |
|---|---|---|
| 떠나요 | xlsx, 예약 단위 | xls(BIFF), 예약 단위, 주 1회(월) |
| 여기어때 | xlsx, 예약 단위 | xlsx, **박 단위**, 주 1회(수) |
| NOL | xlsx, 예약 단위 | 확장자 .xls지만 실제 xlsx, **박 단위**, 사업자 계정별, 주 1회(목) |

- 파일 형식은 확장자가 아닌 매직 바이트로 판별한다.
- 플랫폼/종류는 헤더 시그니처로 판별한다. 같은 플랫폼도 내보내기 화면에 따라 컬럼 구성이 다르므로 헤더 별칭을 지원한다.
- 안내문 행, 합계 행은 건너뛴다.
- 결과로 신규/중복/변경/실패(사유)/미매핑 건수를 반환한다.
- 원본 행은 JSON으로 보존해 파서 수정 후 재처리할 수 있어야 한다.
- **운영 데이터는 정산 파일**을 주 1회 업로드한다 (정산 파일은 1주 단위로만 내려받을 수 있음).
- **과거 데이터는 예약 파일**로 적재한다 (기간 지정 내보내기 가능).

### IMPORT-06 과거 적재와 정산 전환

- **전환월**을 설정한다. 전환월 이후 입실분은 정산 파일이 기준이고, 월 정산서(SETTLE-*)는 전환월부터 생성한다. 전환월 이전 소유주·관리비 정산은 이미 처리된 것으로 보고 다시 만들지 않는다.
- 예약 파일 금액은 `ESTIMATED`로 저장한다. 같은 예약의 정산 행이 들어오면 정산 행이 우선하고 추정 행은 대체된다.
- 과거 데이터의 한계: 박별 금액은 균등 분할 추정, 할인 부담 주체 미상. 취소수수료는 떠나요만 신뢰 가능 (여기어때는 취소 건에도 입금 예정 금액이 남고, NOL은 원래 판매가가 남음) → 여기어때·NOL 과거 취소수수료는 "미상"으로 두고 매출에 넣지 않는다.
- 적재 후 월별 건수·매출 합계를 플랫폼 어드민 숫자와 대조해 검증한다.
- 과거 데이터는 분석(KPI, 수요 예측)에만 쓴다. 예약일시·취소일시가 있어 리드타임, 취소율, Booking Pace 학습 데이터로 오히려 유리하다.

### IMPORT-05 중복 업로드 방지

| 단계 | 방식 | 처리 |
|---|---|---|
| 파일 | 파일 바이트 SHA-256 (`import_batches.file_hash` UNIQUE) | 이전 업로드 일시·업로더를 보여주고 거부 |
| 행 | 자연키 `(source, 예약번호, line_type, stay_date)` UNIQUE | 동일하면 건너뜀(중복), 금액이 다르면 "변경"으로 분류 |
| 변경 행 | 이전 값을 이력으로 남기고 관리자 확인 | 마감된 정산서에 속한 행은 수정하지 않고 다음 달 조정 행 생성 |

- 다시 내려받은 같은 내용의 파일은 바이트가 달라 파일 해시를 통과할 수 있으므로, 행 단위 자연키가 최종 방어선이다.
- 업로드는 **미리보기 → 확정** 2단계로 한다. 미리보기에서 신규/중복/변경/오류 건수를 보여주고, 확정 시에만 저장한다.
- 잘못 올린 배치는 되돌릴 수 있다. 그 배치가 새로 만든 행은 삭제하고, 변경한 행은 이력에서 복원한다. 마감된 정산서에 걸린 배치는 되돌릴 수 없다.
- **업로드 현황표**: 플랫폼·계정(NOL은 사업자 계정 5개) × 주차 격자로 업로드 여부를 표시해 누락을 막는다. 해당 주에 정산이 없으면 "정산 없음"으로 체크한다.

### IMPORT-02 채널과 출처

- **출처(source)**: 데이터가 들어온 경로. DDNAYO / YEOGI / NOL / MANUAL
- **판매 채널(sales_channel)**: 고객이 실제 예약한 곳. 네이버 / 야놀자 / 여기어때 / 떠나요 / 홈페이지 / 전화 / 현장
- 선셋코스트는 떠나요가 네이버·야놀자·홈페이지 예약을 모아 준다. 선셋코스트의 NOL 파일을 따로 올리면 중복이므로 업소별 허용 출처를 설정해 차단한다.

### IMPORT-03 객실 매핑

- 플랫폼별 객실명 → 내부 객실을 `room_aliases`로 매핑한다.
- 매핑 실패, 객실명 잘림, 한 예약에 객실 여러 개인 행은 "확인 필요"로 분류하고 관리자가 지정하면 이후 자동 매칭한다.
- NOL 사업자 계정과 객실 명의가 다르면 경고한다.

### IMPORT-04 예약 파일과 정산 파일의 관계

- 예약 파일: 예약일시, 취소일시, 채널, 상태 등 **수요 데이터의 기준**
- 정산 파일: 박별 금액, 할인(부담 주체별), 수수료, 취소수수료 등 **금액의 기준**
- 예약번호로 연결한다. 정산 파일이 들어오기 전 금액은 `ESTIMATED`(총액 ÷ 박수), 들어오면 `CONFIRMED`.
- 떠나요 정산은 예약 단위이므로 박수로 균등 분할하고 추정 표시한다.
- 취소 건 금액 처리가 플랫폼마다 다르다 (여기어때 예약 파일은 취소 건에도 입금 예정 금액이 남고, NOL 예약 파일은 원래 판매가가 남는다). 취소 건의 금액은 정산 파일의 취소수수료 행만 사용한다.

### RESERVATION-01 직접 예약 입력

전화·현장 예약은 관리자가 입력한다.

- 객실, 체크인, 박수, 인원, 예약자, 박별 금액, 할인, 결제수단, 입금 여부, 메모
- 저장 전 동일 객실·날짜 중복 예약을 검사한다.
- Villa II/III의 전화 예약은 소유주 계좌로 입금되므로 `payment_receiver = OWNER`로 저장하고 매출·소유주 정산에서 제외한다 (점유 현황에만 반영).

### PRIVACY-01 개인정보

- 예약자 연락처는 암호화 저장하고, 재방문 분석용 해시를 별도로 저장한다.
- 원본 파일(docs/YYYYMM*)은 git에 포함하지 않는다.

## 3. 월 정산
### SETTLE-01 공통

- 정산서는 기간 내 예약에서 근거 행을 자동 생성한다.
- 상태: 초안 → 확정 → 지급완료. 지급완료된 정산서는 수정할 수 없다.
- 마감 후 발생한 변경(늦은 취소수수료 등)은 다음 달 정산서의 조정 행으로 반영한다.
- 각 행은 예약번호, 플랫폼, 원본 금액, 업로드 배치/원본 행까지 추적 가능해야 한다.

### SETTLE-02 현장 관리비

- 현장 사장님에게 **예약 1건의 객실마다 1회** 지급한다. 박수와 무관하다 (2박이어도 1회, 2객실 예약이면 객실마다 1회).
- 연박은 **예약번호로만** 판단한다. 같은 손님이 이어서 묵어도 예약번호가 다르면 따로 지급한다 (이름 비교는 마스킹·동명이인 위험이 있어 하지 않는다, 2026-11-13 결정). 예외는 관리자가 예약별로 수정한다.

| 객실 | 단가 |
|---|---|
| 카라반 바다, 노을, 해안, 바람 | 40,000원 |
| 그 외 카라반 (스페이스카라반 4, 에어스트림 5, 고래) | 45,000원 |
| 리조트 (전 호실) | 30,000원 |
| 풀빌라 (PREMIUM, Villa I) | 130,000원 |
| Villa II, III | 0원 (우리가 지급하지 않음, 현장에서 소유주에게 직접 청구) |

- 취소 건은 관리비 없음.
- 단가는 적용 기간과 함께 저장한다.
- 관리자는 예약별로 관리비를 수정할 수 있다 (한달살기 등). 원래 금액과 사유를 남긴다.

### SETTLE-03 외부 소유주 정산

- 대상: Villa II, Villa III
- 기준: **입실일이 속한 월**
- 지급액: 플랫폼 수수료를 뺀 정산금액. 취소수수료도 소유주 몫이다.
- 월 1회 계좌이체. 이체일, 금액, 메모를 기록한다.
- 정산서를 PDF/엑셀로 내보낼 수 있어야 한다.
- 우리 매출 KPI에서는 기본 제외한다 ("단지 전체" 토글로만 포함).

### SETTLE-04 플랫폼 입금 대조

- 정산 파일의 정산일/지급일을 기준으로 주간 입금 예정액과 실제 지급 상태를 보여준다.

## 4. 분석
### KPI-01 매출 대시보드

업소 → 객실 유형 → 객실, 채널, 기간으로 필터한다.

- OCC, ADR, RevPAR, 순RevPAR(수수료 차감)
- 채널 믹스와 실제 수수료율
- 리드타임, 평균 숙박일수, 취소율, 취소수수료 회수율
- Booking Pace (같은 리드타임 기준 전년 대비)
- 할인 효과: 우리 부담 할인과 플랫폼 부담 쿠폰을 구분한다.
- 취소수수료는 매출에는 포함하되 OCC·ADR 계산에서는 제외한다.
- 판매 가능 박수 계산을 위해 객실 차단 기간(`room_blocks`)을 관리한다.

### COST-01 비용과 손익

- 고정비·변동비를 카테고리, 날짜, 금액, 배분 대상(전체/업소/객실 유형/객실)으로 입력한다.
- 관리비는 SETTLE-02에서 자동 반영한다.
- 산출물: 객실 유형별 공헌이익, 손익분기 점유율, 1박당 변동비(가격 하한).

### FORECAST-01 수요 예측 (장기)

- 업소별로 시즌성이 다르므로 업소(또는 객실 유형)별 모델을 둔다.
- 순서: 전년 동기 베이스라인 → Pickup 모델 → Gradient Boosting (공휴일, 방학, 제주 입도객, 날씨 등 외부 변수)
- 분석은 별도 Python 서비스에서 수행하고 결과를 DB에 기록한다.

### PRICING-01 가격 추천 (장기)

- 게시가 이력(`rate_history`)을 기록한다. 팔린 날짜의 가격은 정산 파일에서 복원할 수 있다.
- 규칙 기반 추천부터 시작하고, 1박당 변동비를 하한으로 둔다.
- LLM을 이용한 월간 운영 리포트 자동 작성.

## 5. 개발 순서

1. 데이터 기반: 업소/소유 구조, 예약·정산 라인 스키마, 업로드 파이프라인(중복 방지 포함), 정산 리더 3종, 객실 매핑, 직접 예약 입력
2. 예약 리더 3종, 과거 데이터 일괄 적재와 월별 대조 검증
3. 월 정산: 관리비, 외부 소유주
4. 매출 대시보드
5. 비용과 손익
6. 수요 예측
7. 가격 추천, AI 리포트

### 6.2. 완료된 것

**직접 예약 입력 (RESERVATION-01)** V21, `domain/reservation/service/DirectReservationService`
- `reservations.source = DIRECT`, 예약번호 `D{입력일 yyMMdd}-{순번}`. 채널은 전화(PHONE)·현장(WALK_IN)·기타(OTHER)
- OTA 예약과 같은 구조: 예약 + 예약 객실 + 1박·객실마다 정산 행 (수수료 0, `import_batch_id` NULL, 할인은 `partner_discount`로 금액 비율 분배). 그래서 예약 내역·관리비·채널 분석에 그대로 반영된다
- 추가 컬럼: `guest_count`, `payment_method`, `paid`, `memo`. 연락처는 PRIVACY-01(암호화) 전이라 받지 않는다
- 겹치는 예약(같은 객실, 날짜 겹침, 투숙 상태)은 409 + 목록. `allowOverlap=true`면 저장
- 외부 소유주 객실(Villa II·III)이 있으면 `payment_receiver = OWNER` (화면 매출 합계에서 제외, 관리비 단가 0)

### 6.4. 인증·인가 (feat/auth)

- 로그인: 네이버·카카오 OAuth만 (Spring Security `oauth2Login`). 세션 쿠키(JSESSIONID, 12시간, HttpOnly, SameSite=Lax). 세션은 서버 메모리 (재시작하면 다시 로그인)
- 관리자 화면(Next.js)이 `/api/*`, `/oauth2/*`, `/login/oauth2/*`를 백엔드로 넘긴다 → 쿠키·CSRF 모두 화면 도메인 기준. 백엔드는 `server.forward-headers-strategy: framework`로 X-Forwarded-Host를 믿어 redirect_uri를 화면 주소(`{화면}/login/oauth2/code/{naver|kakao}`)로 만든다. **백엔드를 인터넷에 직접 열면 안 된다** (헤더 위조)
- 네이버·카카오 개발자센터에 등록할 Redirect URI: `{화면 주소}/login/oauth2/code/naver`, `.../kakao`. 키는 환경 변수 `NAVER_CLIENT_ID/SECRET`, `KAKAO_CLIENT_ID/SECRET` (카카오는 Client Secret 사용 설정, 동의 항목 닉네임)
- 역할 `users.role`: SUPER_ADMIN(본사), SITE_MANAGER(현장), USER(일반). 처음 로그인하면 USER → 사용자 관리 화면에서 슈퍼어드민이 바꾼다. 역할은 요청마다 DB에서 다시 읽어 바로 적용 (`CurrentRoleFilter`). 마지막 슈퍼어드민은 내릴 수 없다
- 첫 슈퍼어드민: 로그인 후 '권한 없음' 화면의 계정 키(`KAKAO:123…`)를 `AUTH_SUPER_ADMINS`에 넣고 다시 로그인
- 인가 (`SecurityConfiguration`): `/management-fees/**`·`/admin/**` SUPER_ADMIN, `/auth/**` 로그인한 누구나, 나머지 SUPER_ADMIN·SITE_MANAGER. 예약 목록·상세의 관리비는 SUPER_ADMIN이 아니면 null·빈 목록. 일반 사용자 기능을 만들면 별도 경로(예: `/me/**`)를 `authenticated()`로 연다
- CSRF: 쿠키 `XSRF-TOKEN` → 헤더 `X-XSRF-TOKEN` (`csrf.spa()` + `CsrfCookieFilter`). 화면 `lib/api.ts`가 자동으로 붙인다
- 로컬 개발용 로그인: `POST /auth/dev-login?role=…` (`sunsetcoast.auth.dev-login-enabled`, local 프로필만 true). 로그인 화면에 개발 모드에서만 버튼이 보인다
- Swagger(`/swagger-ui.html`, `/v3/api-docs`)는 로그인 없이 열려 있다. 운영에서는 `springdoc.api-docs.enabled=false` 등으로 끌 것
- 정하지 않은 것: 현장관리자를 업소별로 제한할지 (지금은 모든 업소를 본다)

  `cmd.exe /c "set JAVA_HOME=C:\Users\PC\.jdks\corretto-21.0.10&& cd /d C:\Users\PC\DevSpace\sunsetcoast-api && gradlew.bat test"`
- 테스트: `SettlementFileParsersTest`, `StayCalendarRulesTest`, `ManagementFeeRulesTest`, `MultiRoomTest`, `SampleSettlementFilesTest` (실제 파일 27개, `docs/202610`이 있는 PC에서만 실행됨)
- `docs/202610/` 원본 파일은 고객 개인정보가 있어 git 제외 (`.gitignore`). 집 PC에서 샘플 테스트를 돌리려면 파일을 따로 옮겨야 한다.
